## 1. 블록 B — Actor·권한 (`docs/02` T3, 66~92줄)

| Actor | 역할 | 읽기 범위 |
|---|---|---|
| **수간호사** | 병동의 근무·역할·담당 환자 배정 책임자 | **자신이 관리하는 `ward` 전체** |

### 쓰기는 읽기보다 좁다

- **인계 작성** → `handover.from_care_assignment_id` 당사자만

- **`access_log` 엔티티 없음.** 수간호사의 병동 전체 읽기는 넓은 권한이지만, 감사 로그는 *"실제 도입 시 필요 — 이번 데이터 모델 범위 밖"* 으로 기술서에 명시한다

## 4. 블록 C — 전체 UI 흐름도 (`work/C_UI흐름도.mmd`)

Mermaid. Actor별 레인 2개 + 공통 로그인. **점선 4개가 Actor 간 연결**이다.

```
로그인 ──▶ 수간호사 레인: 대시보드 → 근무등록 → 배정보드 → 재배정 → 변경이력
       └─▶ 간호사 레인:   내 근무 → 인계작성 ⇢ 인계수신·요약확인 → 내 인계이력

점선(Actor 간): 배정 게시(4→8) · 재배정 반영(6→8) · 필수 항목 적용(5→9) · 인계 전달(9⇢10)
```

이 점선 4개가 **"근무 → 역할 → 인계 → 재배정을 하나로 잇는다"** 는 차별점 주장을 그림으로 보여주는 장치다.

## 6. 리뷰에서 특히 봐줬으면 하는 것

1. **기능 5개 ↔ 화면 11개 매핑에 누락·중복이 있는가** — F-04가 화면 4개에 걸쳐 있는데 과한지
2. **권한 규칙이 기능을 막는 곳이 또 있는가** — 이전 리뷰(R29)에서 수간호사가 인계를 못 읽는 문제를 잡았다. 같은 유형이 남아 있는지
3. **401 / 403 / 409 배정이 적절한가** — 특히 F-04의 퇴원 건 `409`
4. **화면 구성 요소가 데이터 모델(11 엔티티)로 전부 뒷받침되는가** — 화면에만 있고 모델에 없는 데이터가 있는지
5. **흐름도의 점선 4개가 실제 화면 전이인지, 데이터 흐름인지** — 표기가 섞여 있는지
6. **수간호사 화면 6개 : 간호사 화면 4개** 비율이 타당한지 (검증 대상자는 간호사 1명이라 수간호사 화면은 가설로 남는다)
