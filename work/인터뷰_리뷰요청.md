# 리뷰 요청 — 1일차 인터뷰 결과가 설계 전제를 깼다

> **이 요청이 DBML 리뷰(5건)보다 급하다.** 그쪽은 규칙의 문제이고, 이쪽은 **전제의 문제**다.
> 전제 판정이 뒤집히면 DBML 수정분 일부가 무의미해진다.

## 0. 시간 제약 — 권고의 현실성 판단에 필요하다

- 3일 설계 과제. **오늘이 1일차 밤.** 남은 시간: **2일차 하루 + 3일차 오전 4시간**
- 2일차 밤에 **대면 사용자 검증 세션(30분)** 이 잡혀 있다. **그 전에 DBML·API 가 굳어야 한다**
- 산출물: 개요 PDF · OAS 3.0.3 YAML · DBML. **실제 개발 없음**
- 평가: 납기 20 / 목표 시스템 정의 30 / **시스템 설계 40(데이터모델 20 + API 20)** / 발표 10
- **감점 아님이 명시된 것**: 평범한 아이디어 · AI 기능 없음 · DB·API 규모 작음 · UI 안 화려함
  → 점수는 **정합성**(문제 → Actor → 기능 → UI → API → DB)에서 난다
- **"설계를 다시 하라"는 권고는 실행 불가능하다.** 지금 필요한 건 **무엇을 고치고 무엇을 스코프로 방어할지**의 판단이다

## 1. 서비스 (현재 상태)

**간호사 교대근무의 인계·배정을 한 곳에서 다루는 웹서비스.** 기획·설계·데이터모델링까지만.

- Actor 2: 수간호사 / 간호사
- 엔티티 11 · Enum 7 · 화면 11 · 기능 F-01~F-06
- 핵심 관계: `shift_assignment → care_assignment → inpatient_stay → handover`
- 차별점으로 잡았던 것: **역할별 필수 인계 항목** + **수신자의 read-back 확인 기록**(I-PASS 의 *Synthesis by receiver*)

### 채택한 Pain 3개 (전부 **관찰** 기반 — 지인이 현직 간호사)

1. **출근해서야 자기 역할(차지/액팅)을 안다**
2. **인계를 제대로 받았는지 확인할 방법이 없다**
3. **결원이 생기면 변경을 여러 곳에 재공지해야 하고, 누가 언제 왜 바꿨는지 안 남는다**

## 2. 인터뷰에서 들은 것 (사실만)

> 현직 간호사 1명, 통화. **편의표본**이며 표기는 항상 *"현직 간호사 1명 확인"* 으로 한다.

### 역할 배정

- **병원마다·병동마다 다르다.** 차지만 하는 간호사·액팅만 하는 간호사를 따로 뽑는 병원도 있다
- 이 병동은 **팀장이 월말 전에 미리 정해 둔다**
- 다만 **간호사들끼리 어느 정도 자유롭게 바꾼다** (경력자가 차지를 선호 / 신규가 오면 액팅 조정)
- **환자 수에 따라 달라지지 않는다**
- 역할은 **3종**: 차지 / **서브차지** / 액팅
  - 데이 **3~5명** = 차지 1 · 서브차지 1 · 나머지 액팅
  - 나이트 **2명 확정** = 차지 1 · 액팅 1 (**서브차지 없음**)

### 인계

- **전산에 남겨 둔 것을 보면서** 차지를 맡은 간호사가 듣는다
- **받는 주 대상은 차지.** 액팅은 **옆에서 같이 들으며 본인에게 필요한 부분만 체크**
- **누가 들었는지 확인하는 기록 시스템은 없다.** *"그날 차지가 듣는 게 당연한 구조"*
- **전산에는 진짜 필요한 내용만** 담기고, 사소하지만 알면 좋은 것은 **구두로만 전달되어 기록이 남지 않는다**

### 담당 환자

- **A팀 / B팀**으로 나누고 **팀 단위로 담당.** A팀은 몇 호실~몇 호실, B팀은 다른 호실 — **호실 범위** 기준
- **팀은 근무표 단위가 아니라 거의 고정.** 팀 간 이동은 **한 달에 한 번 있을까 말까**
- **팀 안에서 액팅별로 환자를 나누지 않는다.** 팀이 공동으로 본다 (액팅 인원이 많지 않아 그렇게 구조화할 필요가 없다)

## 3. 내가 내린 판정 4개 — 이것이 리뷰 대상이다

### P1. 모델 전제 2개가 현장과 다르다

| | 모델 전제 | 현장 |
|---|---|---|
| 인계 당사자 | `handover.from/to_care_assignment_id` — **환자 1건당 담당자 ↔ 담당자** | **전 근무 차지 ↔ 다음 근무 차지.** 액팅은 참관 |
| 담당 배정 단위 | `care_assignment(shift_assignment_id, inpatient_stay_id)` — **개인 ↔ 입원 건** | **팀(고정) ↔ 호실 범위 → 그 호실 환자들.** 팀 공동 |

### P2. Pain 1 이 이 병동에서 성립하지 않는다 → **축을 인계로 옮긴다**

- 역할은 **월말 전에 안다.** 팀이 고정이고 호실 범위도 고정이므로 **담당 환자도 대체로 미리 안다**
- → *"출근해서야 안다"* 는 **틀렸다**
- 살아남는 각도: **"간호사끼리 바꾼 뒤의 최신 상태가 한 곳에 없다"**

**판정**: Pain 1 을 **보조 기능**으로 내리고 서술을 위 문장으로 정정. **Pain 2(인계)를 전면에** 세운다.
Pain 2 는 오히려 강해졌다 — **확인 기록 시스템이 없다는 것이 확인**됐기 때문이다.
서비스명이 이미 인계 중심(`너와나의인계고리`)이라 정합적이라고 봤다.

### P3. `care_assignment` 를 **"그 근무의 책임자"** 로 재정의하고 **차지에게만** 생성한다

팀 공동 담당이므로 개인 ↔ 환자 배정 행위가 현장에 **없다.** 그러나 **인계를 받는 책임자는 차지 1명**이고 이것은 사실이다.

```
care_assignment = "이 근무조에서 이 입원 건의 책임자"   → 팀의 차지에게만 생성
handover        = 차지의 care_assignment → 차지의 care_assignment   (현장과 일치)
```

**같이 추가하는 것**

- `Table team(id, ward_id, name)` · `users.team_id` · `inpatient_stay.team_id` → 엔티티 11 → **12**
- **읽기 권한 3단**: ① 병동(수간호사) ② `care_assignment` ③ **같은 팀·같은 근무** ← 액팅 참관을 표현
- `role_type` 에 **서브차지** 추가 (스키마 변경 없음 — 테이블로 둔 덕분)

**검토했지만 채택하지 않은 대안**

> `care_assignment` 를 없애고 `handover.from/to` 를 `shift_assignment` 기준으로 재설계.
> **현장에 더 가깝다.** 그러나 `handover` · `handover_item` · `handover_receipt` · `reassignment_log` 의 FK 가
> 전부 바뀌고, 어제 작업한 `SUPERSEDED`(수신자 결원 시 인계 승계) 와 불변 규칙 8개 중 3개를 재작성해야 한다.
> **남은 시간에 리뷰 사이클을 한 번 더 돌릴 수 없다고 판단했다.**

### P4. 대상 범위를 **병동 1곳**으로 좁힌다

> **"국내 종합병원 병동 1곳의 운영 방식을 기준으로 설계했다.
> 현직 간호사 1명 인터뷰로 확인했으며, 병동마다 운영이 다르다는 것도 같은 인터뷰에서 확인했다."**

- Out of scope 에 **"병동별 운영 차이(차지 전담 채용 등)"** 명시
- 병원명·개인이 드러나는 표현은 쓰지 않는다

## 4. ★ 특히 판단해 줬으면 하는 것

1. **P2 가 과잉 반응인가.**
   Pain 1 을 내리면 F-02·F-03(내 근무·역할 확인)이 서비스에서 **왜 존재하는지**가 약해진다.
   *"바뀐 뒤의 최신 상태가 한 곳에 없다"* 가 **F-02·F-03 을 지탱할 만큼의 pain 인가**,
   아니면 **Pain 3(결원 재배정)에 흡수시키고 화면만 남기는 게 정직한가**?

2. **P3 이 "현장에 맞추는 척" 인가.**
   `care_assignment` 는 이름이 *"담당 배정"* 으로 읽히는데 실제 의미는 *"책임자"* 다.
   - **테이블명을 바꿔야 하는가** (파급: FK 8곳 + 문서 3개 + 목업). 아니면 note 와 발표 설명으로 충분한가
   - 팀 공동 담당인데 **차지에게만 행을 만드는 것**이, 정합성 심사에서
     *"현장에 없는 개념을 만든 것"* 으로 읽힐 위험은 없는가

3. **P3 의 대안(shift 기준 재설계)을 포기한 판단이 맞는가.**
   남은 시간(2일차 하루 + 3일차 오전 4시간)에 **정말 불가능한가**,
   아니면 **전제가 틀린 채로 제출하는 것이 더 큰 감점**인가

4. **Pain 2 의 서술을 어디까지 말할 수 있는가.**
   확인된 사실: ① **확인 기록 시스템 없음** ② **인계 내용 자체는 전산에 남음**
   ③ 사소한 것은 **구두로만 전달되어 기록이 안 남음**
   - *"기록이 없다"* 가 아니라 **"받았다는 기록이 없다"** 로 좁혔는데, 이 구분이 충분히 된 표현인가
   - ③ 을 근거로 **"구두 내용도 기록하게 하자"** 로 가면 안 된다고 봤다(구두로 남기는 데는 이유가 있다).
     이 판단이 맞는가, 아니면 **기회를 버리는 것인가**

5. **읽기 권한 3단이 또 과잉인가.**
   이전 라운드에서 *"권한이 자기 기능을 막는"* 실수를 두 번 했다(수간호사가 인계를 못 읽음 → 3단 분리).
   ③ 같은 팀·같은 근무를 추가하는 것이 **액팅 참관을 표현하는 최소 수단**인가

6. **발표 시나리오로 잡은 것이 현장에 맞는가.**
   **나이트(차지 1 · 액팅 1)에서 차지 결원** → 대체 지정 → 담당 이관 → 인계 수신자 변경(`SUPERSEDED`) → 확인.
   기능이 한 줄로 꿰이지만, **인원이 2명뿐인 시간대를 대표 시나리오로 쓰는 것**이 과장인가

## 6. 판단에 필요한 다른 사실

- 실제 환자정보 **미사용** — 가상 입원 건만
- 엔티티 11(→12)은 `[전략] 6~9개` 기준의 **의도적 예외**
- 앞선 리뷰 이력: 10라운드 · 51건. 반복된 실패 패턴 두 가지
  - 초반: **사실 → 결론 추론 과잉** (찾지 못한 것을 없다고 씀)
  - 최근: **한 규칙이 여러 파일에 흩어지고, 고칠 때 한 곳만 고침**
- 별도로 대기 중인 DBML 리뷰 5건: 권한 판정(`user_type`) · `SUPERSEDED` · 템플릿 기준 역할 ·
  `change_reason` 복사 · 인덱스 누락 — **전부 반영 완료.** 이번 판정에 따라 일부가 무의미해질 수 있다
