# 이전 기수 우수 산출물 분석 — 배울 점과 규모 기준

대상: `SKALA 스마트 교육플랫폼 — 과제 및 피드백 통합 관리 시스템` (참고자료 PDF 29p + DBML + API.yml)

> ⚠️ **이 산출물을 베끼거나 변형해서 쓰지 않는다.** 여기서 가져올 것은 *구조와 작성 습관*이지 내용이 아니다.

---

## 1. 규모 캘리브레이션 — "이 정도면 충분하다"의 기준선

| 항목 | 참고자료 실측 | 3일 솔로 권장 |
|---|---|---|
| Actor | 3명 (관리자 / 교수자 / 교육생) | **2~3명** (관리자는 얇게) |
| 화면(HTML) | 13개 | **10~13개** (교안 "최소 10개 이상") |
| 테이블 | 8개 + Enum 5개 | **6~9개 + Enum 3~5개** |
| API 엔드포인트 | 약 28개 오퍼레이션 | **20~30개** |
| 기술서 슬라이드 | 27장 (Appendix 포함) | **20~25장** |

> 규모가 작아도 감점이 아니다. 다만 **화면 10개는 사실상 하한선**이고, 그 10개가 기능 목록을 전부 덮어야 한다.

---

## 2. 배울 점 10가지

### (1) UI 목업 위에 API를 직접 주석으로 얹었다 — 정합성의 시각적 증명
화면 캡처 옆에 `GET /courses/my`, `GET /activities/pending` 같은 엔드포인트를 화살표로 연결하고,
"현재 로그인한 사용자의 역할에 따라 다른 강좌 목록 반환" 식으로 **동작까지 한 줄 설명**했다.
→ 평가자가 UI·API·DB를 따로 대조할 필요가 없어진다. **가장 확실한 득점 장치.**

### (2) 주석 색 범례를 명시했다
`초록 = UI 이동` / `빨강 = API 및 기능 설명` / `파랑 = 모달 창 등 특이사항`.
범례 한 장으로 이후 10여 장의 화면 슬라이드가 전부 읽히게 만들었다.

### (3) 전체 UI 흐름도를 Actor별 레인으로 그렸다
관리자 / 교수자 / 교육생 3개 박스로 나누고, 각 노드에 **화면 파일명(`1_login_main`, `5_dashboard_professor`)** 을 적어뒀다.
→ 흐름도 노드 ↔ 목업 파일 ↔ 상세 슬라이드가 **같은 ID로 1:1 대응**된다. 이름 규칙 하나로 정합성이 공짜로 따라온다.

### (4) 기획 배경에 '증거'를 넣었다
Slack 스레드 캡처와 Google Forms 캡처를 붙이고 "기존 방식은 교수자·교육생 모두 불편 → 과제 관리 시스템 필요"로 연결했다.
→ 배경이 상상이 아니라 **관찰**임을 보여준다. 세부 평가 기준의 "구체적인 문제 정의(원인·배경·현황 포함)" 항목을 정면으로 충족한다.

### (5) Pain point ↔ Solution을 1:1 표로 대응시켰다
Pain 3개(Actor 표기 포함) → Solution 3개. 이후 기능 목록이 이 3개에서 파생된다.
→ "기능이 문제 해결과 연결되지 않음"이라는 감점 사유를 원천 차단.

### (6) 파생 데이터를 컬럼으로 만들지 않고, 그 판단을 DBML 주석에 적었다
- `수강 상태`(예정/중/완료) → 컬럼 없이 `start_date·end_date`와 현재 시각 비교로 서버 계산, 응답 필드 `enrollment_status`로 반환
- `지각 제출 여부` → 컬럼 없이 `submitted_at` vs `deadline` 비교, 응답 필드 `is_late`로 반환
→ **판단을 설명한 주석 자체가 점수다.** 결과물만으론 "안 만든 것"과 "일부러 안 만든 것"을 구분할 수 없다.

### (7) 유사 엔티티를 Enum 타입 컬럼으로 통합했다 (Single Table Inheritance)
과제·퀴즈를 각각 테이블로 쪼개지 않고 `activities` 하나 + `type ActivityType` 으로 처리.
슬라이드에 "토론·설문 조사 등 추가 시 유연한 대응 가능"이라고 **확장성 논거**까지 적었다.
→ 설계는 선택이고, **선택의 근거를 말하는 것이 설계 역량의 증거**다.

### (8) 제약조건을 인덱스로 표현했다
`(student_id, course_id) [unique]` — 중복 수강 방지
`(activity_id, student_id) [unique]` — 한 활동당 한 제출
`(submission_id, question_id) [unique]` — 문항 중복 답안 방지
→ "PK/FK 및 관계가 적절한가" 항목에서 한 단계 위로 올라간다.

### (9) OAS를 components부터 설계했다
`PagedResponse` 목록 래퍼 / `Error` 공통 스키마 / `BadRequest·Unauthorized·NotFound` 공통 응답 / `PageParam·SizeParam` 공통 파라미터.
Appendix에서 **"시스템 전역 공통 스키마 / 도메인 공통 스키마"** 로 색을 나눠 재사용 구조를 설명했다.
→ 세부 평가 기준의 "공통 스키마 재사용($ref)" 항목 직격.

### (10) 화면 단위 전용 API를 별도로 설계했다
`/activities/pending`(미제출 목록), `/submissions/recent`(최근 피드백), `/activities/pending-grades`(채점 대기).
리소스 CRUD만 만들면 대시보드 화면이 API 없이 남는다 → **"UI에서 필요한 API 누락"** 이 가장 흔한 감점이다.

## 3. 참고하되 그대로 따르지 않을 것

| 항목 | 참고자료 | 우리 판단 |
|---|---|---|
| Actor 3명 전부 두껍게 | 관리자도 사용자/강좌 CRUD 풀세트 | 3일 솔로면 **관리자는 승인·등록 정도로 얇게**. 화면 2개면 충분 |
| 인증 상세 | JWT·역할 접두사 규칙까지 기술 | **Security Schemes는 평가 제외.** `info.description` 한 줄로 끝낸다 |
| 도메인 | 교육 플랫폼(LMS) | **같은 도메인은 피한다.** 비교당할 이유가 없다 |
| 페이지네이션 | 전 목록 API에 적용 | 넣으면 가점이지만, **정합성이 우선**. 시간 남을 때 |

---

## 4. 이 분석에서 나온 실행 규칙 5줄

1. 화면 ID를 **`번호_화면명_actor`** 로 정하고, 흐름도·목업 파일·슬라이드에 동일하게 쓴다.
2. 모든 화면 캡처에 **호출 API를 빨간 주석**으로 얹는다. 범례 슬라이드를 앞에 둔다.
3. **파생값은 컬럼으로 만들지 않고, 안 만든 이유를 DBML 주석에 적는다.**
4. OAS는 **components → paths** 순서로 쓴다.
5. 대시보드·요약 화면에는 **전용 조회 API**를 따로 만든다.
