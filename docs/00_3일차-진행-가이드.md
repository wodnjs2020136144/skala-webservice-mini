**세부 평가 기준에 명시된 것** [필수]

- **UI ↔ API 데이터 필드 일치**, PK/FK 명시 및 관계(1:N, M:N), 속성 **데이터 타입 및 제약조건** 명시

- **Security Schemes는 평가 제외**
- **예외/오류 시나리오 포함은 가점** [권장]

> 즉 점수는 **규모·참신함이 아니라 정합성**에서 난다.
> `문제/목적 → Actor → 기능 → UI → API → DB` 가 끊김 없이 이어지는지를 본다.

## 2. 3일 내내 유지할 척추 문서 — 화면·API·데이터 매핑표 [전략]

세 산출물(기술서 PDF / API.yml / DB.dbml)을 따로 쓰면 어긋난다. **표 한 장을 단일 출처로 두고 세 파일을 파생**시킨다. (템플릿 `docs/02_작업-템플릿.md` T6)

```
기능ID | 화면ID | Actor | 트리거 | Method | 경로 | 요청 | 응답 필드 | 데이터 근거 | 예외(코드)
```

**표의 4가지 규칙 — 기본은 지키고, 예외는 사유를 한 줄 적는다**

1. 화면에 **보이는 모든 값**은 어느 API의 응답 필드에 존재한다.
2. 응답 필드의 모든 값은 **테이블 컬럼**이거나 `서버 계산`으로 표시된다.
3. 기능 목록의 **모든 기능 ID**는 최소 한 행에 등장한다. ← 이 규칙 때문에 표에 `기능ID` 열이 필요하다
4. 표에 한 번도 안 나오는 API·테이블·컬럼은 **삭제하거나, 남기는 이유를 T6-b에 기록**한다.

> ⚠️ 4번의 정당한 예외: 감사 로그, 이력 스냅샷(주문 시점 가격처럼 **그때의 값**을 보존해야 하는 것), 내부 FK, `created_at`/`updated_at`, 성능용 비정규화.
> **이 예외를 기록해 두면 그대로 '설계 고민' 슬라이드 재료가 된다.** 지우는 것보다 점수가 높다.

## 6. 흔한 실패 5가지

1. **주제가 커서 화면을 다 못 그린다** → 1일차 오전 Out of scope로 차단
2. **DB를 먼저 그리고 화면을 끼워 맞춘다** → `화면 → 필드 → 엔티티` 순서 고정
3. **세 산출물을 따로 쓴다** → 매핑표 단일 출처에서 파생
4. **3일차에 PDF를 처음 조립한다** → 1일차 골격 + 산출 즉시 삽입으로 차단 ← **리뷰가 잡아낸 최대 위험**
5. **UI 흐름도 누락 / 파일명 오류** → 배점이 통째로 날아간다
