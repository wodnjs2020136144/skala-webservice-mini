## 1장. 서비스 개요

**서비스명** — 너와나의인계고리

> **[교대근무 병동의 간호사와 수간호사]** 가 **[교대 때 인계를 주고받고, 결원으로 바뀐 배정을 다시 맞춰야 하는 상황에서]**
> **[인계를 누가 받아 이해했는지 남는 기록이 없고, 배정이 바뀌면 여러 곳에 다시 알리고 최신본을 확인해야 해서]** 불편한데,
> 이 서비스로 **[누가 무엇을 맡았고 무엇을 주고받았는지 확인하고, 그 기록을 남길 수 있다]**.

**핵심 가치**

> **근무표가 끝나는 지점에서 시작한다.** 누가 나오는지까지만 말하는 근무표에,
> **누가 인계를 맡았고 누가 받아 확인했는지**를 붙여 한 줄로 잇는다.

**하지 않는 것** — 근무표 자동 생성 · 실제 EMR 연동 · 실제 환자 개인정보 · 임상적 판단/추천 · 교육 일정/급여

## 2장. 배경 — 무엇이 비어 있나

- 국내 직접 경쟁 후보 **13건**(국내 12 + 일본 개발 1) 중 **확정 근무 → 당일 역할 → 구조화 인계 → 결원 재배정을 하나의 흐름으로 연결한 사례는 확인하지 못했다** `[B]` — 제품 공식 페이지·앱스토어 설명 기준
- 해외에는 있다 — Epic "Art"(교대 노트 AI 생성 · 배정 제안) `[B]` Epic 공식 포스트 / ShiftSBAR(개인용 SBAR 변환) `[B]` 제품 페이지
  - Epic 은 **미국 EHR 내장**이라 국내 병동의 선택지가 아니고, ShiftSBAR 는 **개인 도구**라 병동 단위 배정·수신 확인·이력이 없다
- 건강정보는 **민감정보**로 처리가 제한되지만 **별도 동의·법령 근거가 있으면 처리 가능**하다 `[A]` 개인정보보호법 제23조
  - → 빈 이유가 *"법적으로 불가능"* 이 아니라 **비용**(동의 설계 · 접근 통제 · 병원 승인 · EMR 연동 책임)이라는 것은 **우리의 해석**이다. 등급을 붙이지 않는다
- 국내 EMR 의 교대 인계 전용 워크플로 유무는 **`[D]` 미확정** — 인증기준·공개자료에서 확인하지 못했고, **"없다" 는 뜻이 아니다**

> ⚠️ **발표에서 "없다" 라고 말하지 않는다.** *"조사 범위에서 확인하지 못했다"* 로 말한다.

**조사 범위와 한계**

- 대상: **국내 종합병원 병동 1곳** `[C]`. 현직 간호사 **1명** 인터뷰(편의표본)로 확인했고, **병동마다 운영이 다르다는 것도 같은 인터뷰에서 확인**했다 `[C]`
- 결과는 *"간호사 일반의 의견"* 이 아니라 **"현직 간호사 1명을 대상으로 한 탐색적 확인"** 이다
- **등급 표기 규칙** — 이 원고의 모든 사실 주장에는 `[A]`~`[D]` 중 하나를 붙인다. 등급이 없는 문장은 **우리의 설계 판단**이지 사실 주장이 아니다

## 4장. 시스템 액터와 권한

| Actor | 범위 |
|---|---|
| **수간호사** | 병동의 근무·역할·인계 담당 배정 책임자 `[C]`. 자신이 관리하는 `ward` 전체를 읽는다 |
| **간호사** | 내 근무·역할은 `shift_assignment`, 우리 팀 환자는 `inpatient_stay.team_id`, 인계 담당은 `handover_assignment` 기준 |
| **다른 병동** | 접근 금지 — 병동 경계가 곧 권한 경계 |

### 읽기 3단 — 권한이 기능을 막지 않게

| 단계 | 대상 | 판정 |
|---|---|---|
| ① | 병동 전체 | `user_type = HEAD_NURSE` + `users.ward_id` 일치 |
| ② | 내가 인계 담당인 입원 건과 그 인계 | 내 `shift_assignment` 의 `handover_assignment` |
| ③ | **우리 팀 환자와 그 인계** | 인계의 `from`/`to` 근무가 **내 `ACTIVE` 근무와 같은 병동·날짜·근무조** + 같은 팀 + **`sent_at` 있음** |

> **③ 이 없으면 액팅이 차지가 받은 인계를 못 읽는다.** 규칙이 자기 기능을 막은 실수를 두 번 했고, 두 번 다 이 표에서 잡았다.
> **쓰기는 더 좁다** — 작성은 `from` 당사자, 요약·확인은 `to` 당사자만.

## 8장. 데이터 모델 `[배점 20]`

`[캡처] assets/erd_full.png` — **12 테이블 · 7 Enum · FK 23**

### 핵심 설계 포인트 ① `handover_assignment` — 이름이 뜻을 바꿨다

- 1일차: `care_assignment` = *"환자의 개인 담당자"*
- 인터뷰: **팀이 환자를 공동 담당한다** `[C]` → 개인 ↔ 환자 배정 행위가 **현장에 없다**
- 현재: **`handover_assignment` = "그 근무에서 이 입원 건의 인계를 작성·수신할 차지를 지정하는 경로"**
- 팀의 환자 범위는 이 테이블이 아니라 **`inpatient_stay.team_id`** 로 표현한다
- **역할로 강제하지 않는다** — 차지 결원 시 누가 올라가는지 확인되지 않았고, 확인되지 않은 운용을 DB가 금지하면 안 된다

### 핵심 설계 포인트 ② 과거 인계는 불변이다

- `handover_assignment` 는 **append-only**(`REPLACED` 보존), `handover_item` 은 **템플릿 스냅샷**
- 수신자가 결원되면 덮어쓰지 않고 **`SUPERSEDED` 로 보존 + 후속 인계 발행**(`superseded_by_handover_id`)
- `CONFIRMED → SUPERSEDED` 는 **금지(409)** — 확인까지 끝난 인계는 닫힌 고리다
- **대가도 적는다**: 남긴 행은 여전히 유효한 ID라서, **읽기·쓰기·선택 세 곳에서 "이 행이 현재인가"를 검사**해야 한다

### 핵심 설계 포인트 ③ 결원 이력은 두 층위다

- 근무 자리(`shift_assignment`)와 인계 담당(`handover_assignment`) — **담당 0건 결원도 이력이 남아야 한다**
- `change_type` 하나로 네 FK의 유효 조합을 결정한다(다형성 FK는 쓰지 않았다 — FK 제약을 걸 수 없다)

## 9장. API `[배점 20]`

`[캡처] assets/swagger_full.png` — **24 오퍼레이션 · 21 경로** · 스펙 에러 0
`[검사] python3 tools/deck_check.py` — 슬라이드의 모든 API 주소가 OAS 에 실재하는지 자동 대조

### 설계 포인트 ① 요청에서 받지 않는 값 — `서버 계산`

| 값 | 왜 서버가 정하는가 |
|---|---|
| 인계의 `to` | 요청이 주면 **임의의 과거·미래 근무**로 보낼 수 있다 → 같은 입원 건의 **시간상 다음 `ACTIVE` 인계 담당**, 없으면 `422` |
| `change_reason` | 사람이 쓰는 지점은 **결원 등록 하나뿐**. 나머지는 복사 — 사유가 갈리면 한 건의 이력을 이어서 못 읽는다 |
| `is_handover_owner` · `incoming/outgoing_handover_id` | 화면 버튼(작성/확인/열람)을 **서버가 판정**한다. `SUPERSEDED` 는 제외 |

### 설계 포인트 ② 상태 전이가 오류 코드를 만든다

- `DRAFT → SENT → CONFIRMED` · `DRAFT/SENT → SUPERSEDED`
- **`409`** 는 전이 금지(역행·재확인·`SUPERSEDED` 쓰기), **`422`** 는 입력 부족(필수 항목·요약 미입력·가드 불충족)
- **타 병동 리소스 접근**은 `404` 가 아니라 **`403`** 으로 답한다 — 권한 경계를 명시적으로 드러내는 쪽을 택했다(사유는 T6-b).
  존재하지 않는 리소스는 그대로 **`404`** 다. 둘을 합친 것이 아니다

## 10장. 설계 고민 · 한계 · 향후

### 설계 고민 (T6-b 에서 그대로 가져온다)

- 대시보드는 **화면 전용 집계 API** — 4개 리소스를 합친다. 나누면 집계 규칙이 클라이언트로 흩어진다
- 열람 기록(`received_at`)을 **`GET` 과 분리** — `GET` 에 부작용을 넣으면 수간호사·액팅의 열람도 수신 기록이 된다
- 잔여 담당은 **API 가 아니라 화면**이 막는다 — 이관하지 않는 것이 정상인 경우가 있다

### 한계 — 정직하게 적는다

1. **EMR 연동이 없다.** 공식 의무기록은 EMR, 이 설계는 **인계장(카덱스) 계층**만 다룬다. **대체가 성립하는지는 검증 전이다** — 병행 운용이면 이중 입력이 남는다
2. **차지가 인계 작성 요청을 무시해도 현재 설계는 막지 못한다** — 액팅 의견의 채택·거부 이력은 범위 밖
3. **과거 인계의 액팅 열람은 범위 밖** — `users.team_id` 는 현재 소속이라 팀 이동 뒤 과거 판정이 부정확하다
4. **검증 표본 1명** — 간호사 화면은 1명 검증, 수간호사 화면은 **가설**이다
5. 감사 로그(`access_log`)는 이번 모델에 없다 — 실제 도입 시 필요

### 마무리 — 검증 방식

> **"국내 종합병원 병동 1곳의 운영 방식을 기준으로 설계했다.
> 현직 간호사 1명 인터뷰로 확인했으며, 병동마다 운영이 다르다는 것도 같은 인터뷰에서 확인했다."**

> **"공식 의무기록은 EMR 이 맡고, 교대 인계 메모는 그와 분리되어 관리된다.
> 이번 서비스는 그 인계 메모 계층을 대체해 작성 주체 · 수신 확인 · 변경 경로를 기록한다."**

- 설계 판단은 **27라운드**의 리뷰 반영 이력으로 남아 있다(`docs/04`)
- 목 데이터 데모로 규칙을 실제로 실행해 확인했다 — 스모크 **50/50** · 응답 필드와 OAS 의 **차집합 0**(`tools/oas_field_check.py`)
- 전제가 무너진 것 4개를 **철회로 기록**했고, 그중 3개가 설계를 줄였다
