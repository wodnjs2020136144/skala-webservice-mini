|---|---|---|---|---|---|---|---|---|---|
| F-01 | | | 화면 진입 | GET | | | | | 401, 403 |
| F-02 | | | 저장 클릭 | POST | | | | | 400, 409 |

**4가지 규칙 — 기본은 지키고, 예외는 T6-b에 사유를 적는다**

1. 화면에 보이는 모든 값 → 어느 행의 응답 필드에 존재
2. 응답 필드의 모든 값 → 테이블 컬럼이거나 `서버 계산`
3. 모든 기능ID → 최소 1행에 등장
4. 표에 없는 API·테이블·컬럼 → 삭제하거나 **사유 기록**

## T6-b. 설계 예외 기록 ★ 신설

> 원칙을 벗어난 결정만 적는다. **이 표가 그대로 기술서 8장(설계 고민)이 된다.**

| 대상 | 원칙 | 실제 결정 | 사유 |
|---|---|---|---|
| 예) `order.price_at_order` | 파생값은 컬럼으로 두지 않는다 | 컬럼으로 저장 | 주문 시점 가격을 보존해야 함. 현재가로 재계산하면 과거 주문이 왜곡됨 |
| 예) `audit_log` 테이블 | 화면에 안 나오는 테이블은 삭제 | 유지 | 권한 변경 이력 추적용. 화면 없음이 정상 |
| 예) `department` | 상태·유형값은 Enum | 별도 테이블 | 관리자가 값을 추가·수정하므로 Enum이면 배포가 필요해짐 |

## T8. OAS 작성 순서

1. `openapi: 3.0.3` + `info` (인증 방식은 여기 description에 한 줄)
2. `servers` → 3. `tags`
4. `components/schemas` — 엔티티 응답 + `PagedResponse` + `Error`
5. `components/responses` — `BadRequest` `Unauthorized` `Forbidden` `NotFound`
6. `components/parameters` — `PageParam` `SizeParam`
7. `paths` — T6 표 순서대로

### API 체크리스트

**[필수]**

- [ ] 적절한 HTTP Method / Path·Query·Body 명확히 정의
- [ ] 모든 오퍼레이션에 성공 응답 + **에러 코드(400·401·403·404 등)** 정의

## T9. 3일차 검증 (09:00–10:15)

### (1) 존재 대조

| 방향 | 확인 내용 | 발견한 불일치 | 조치 |
|---|---|---|---|
| UI → API | 모든 버튼·데이터에 대응 API가 있는가 | | |
| API → DB | 응답 필드마다 컬럼 또는 `서버 계산` 근거가 있는가 | | |
| DB → UI | 어느 화면에서도 안 쓰이는 테이블·컬럼이 있는가 | | |

### (2) 정상 흐름 밖 점검 ★ 신설

| 점검 | 질문 | 결과 |
|---|---|---|
| **권한** | 허용되지 않은 Actor가 호출하면? `401`(미인증)과 `403`(권한없음)을 구분했는가 | |
| **경계값** | 빈 목록 → `200` + 빈 배열인가 | |
| | 중복 생성 → `409`인가 | |
| | 존재하지 않는 ID → `404`인가 | |
| **상태 전이** | 허용되는 상태 변경 순서를 적었는가 | |
| | 금지되는 역행(예: `완료 → 대기`)을 막았는가. 위반 시 코드는? | |

> 상태 전이는 **표 하나로 그리면 발표에서 강하다**: 행=현재 상태, 열=목표 상태, 칸=허용/금지+코드
