## 1. 기본 루프 (3단계)

```
주 작업자 → 독립 비평자 → 주 작업자 반영 + 기계 게이트
```

### 1-1. 주 작업자: 작업 계약을 쓴다

조사 보고서·장문 계획서를 따로 만들지 않는다. **이 계약 하나만** 둔다.

```markdown
# Task contract
- 목표:
- 완료 조건:          ← 기계로 판정 가능하게 쓴다
- 고위험 가정:        ← 틀리면 전체가 무너지는 전제
- 변경 가능 범위:
- 검증 방법:
```

**코드 작업이면 계약 뒤에 바로 구현한다.** §2 위험도 점수가 높을 때만 구현 전에 멈춘다.

### 1-2. 독립 비평자: 다른 모델 계열

- ★ **1라운드에는 작성자의 사고 과정·기각 대안·자기의심 노트를 주지 않는다.**
  원 요구사항 + 작업 계약 + 실제 산출물(또는 diff)만 준다
- **차단 지적 최대 5개.** "개선하면 좋은 점"은 분리해서 따로 받는다
- 형식: `ID / 심각도 / 실패 시나리오 / 근거 / 가장 작은 검증법`
- **읽을 파일은 시작 목록일 뿐이다.** 주장 검증·영향 범위 확인에 필요하면 추가로 읽는다.
  **추가로 읽은 파일과 이유를 리뷰 끝에 기록한다**

### 1-3. 주 작업자: 반영 + 게이트

| 상태 | 필요한 근거 |
|---|---|
| `accepted` | 변경된 계획·코드·문서의 **위치** |
| `rejected` | 재현 결과 · 테스트 · 원문 페이지 · **명시적 사용자 결정** 중 하나 |
| `unresolved` | 선택지별 비용 + 사람이 답할 질문 **하나** |

★ **`contract.md` 와 `review.md` 는 같은 `task_id` 를 가져야 한다** (리뷰 V22-02).
없거나 다르면 게이트가 거부한다 — 이전 작업의 리뷰가 새 작업을 통과시키던 구멍이었다.

★ **차단 지적마다 본문 섹션이 있어야 한다** (리뷰 V22-03). 표는 상태 원장일 뿐이다.

```markdown
### V1 / 치명 / 제목
**실패 시나리오**: …
**최소 검증법**: …
```

★ **기각 사유의 길이가 아니라 반증 가능한 근거의 존재가 게이트다.**

> ⚠️ **게이트가 보증하지 않는 것** — 게이트는 근거의 **유형과 최소 형식**만 검증한다
> (`path` 는 파일 실존까지, `source` 는 locator 존재까지, `test` 는 명령+결과 형태까지).
> **근거의 사실성은 검증하지 않는다.** test 명령을 재실행하지 않고, 인용문이 원문과
> 일치하는지 확인하지 않는다. 그건 비평자 또는 사람이 확인해야 한다 (리뷰 V21-04).
`치명` 등급 `unresolved`가 있으면 자동 중단하고 사람에게 넘긴다.

## 2. 절차 선택 — 위험도 5문항

파일 수는 위험도가 아니다(v1의 오류). 아래 질문에 `예`를 센다.

| # | 질문 | `예`일 때 추가 |
|---|---|---|
| 1 | 틀리면 복구·제출 취소가 비싼가? | 구현 전 설계 리뷰 |
| 2 | 자동 테스트로 정답을 확인하기 어려운가? | 독립 근거 대조 |
| 3 | 여러 모듈·소비자·문서에 영향이 퍼지는가? | 영향 범위 조사 |
| 4 | 요구사항이 모호하거나 처음 다루는 영역인가? | 대안 비교 |
| 5 | 외부 사용자·평가자에게 바로 노출되는가? | 구현 후 리뷰 |

**판정은 아래 하나만 정본이다.** (v2 의 "문항별 추가 절차"와 "합산 점수"가 동시에
권한을 갖던 모순을 제거했다 — 리뷰 V2-01)

| 점수 | 절차 |
|---|---|
| **0점** | 단독 작업. 루프 안 돌린다 |
| **1점** | **해당 문항의 추가 절차만** 수행한다 (위 표) |
| **2–3점** | 기본 3단계 루프 |
| **4–5점** | 확장 — 구현 전 설계 리뷰 + 구현 후 리뷰 |

★ **단, Q1(복구 비용)과 Q5(외부 노출)는 점수와 무관하게 각각 구현 전·후 리뷰를 강제한다.**
다른 문항이 모두 `아니오`여도 단독 처리하면 안 되는 유일한 두 경우다.

> 점수는 시범 운영 6건 뒤 조정한다.

## 3. 워크로드 A — 수업 자료 정리 (별도 파이프라인)

**핵심 위험은 설계 오류가 아니다.** 원문 누락 · 숫자 오독 · 코드 왜곡 · 세 산출물 간 불일치다.
따라서 코드용 절차를 그대로 쓰지 않는다.

1. PDF를 페이지 이미지로 렌더링하고 **`페이지 → 주제` 색인**을 만든다
2. **시각 입력을 안정적으로 다루는 쪽**이 주 작업자가 되어 산출물을 쓰고,
   핵심 주장마다 **페이지 번호**를 남긴다
3. **`coverage.tsv` 로 페이지별 처분을 기록한다** — 모든 페이지가
   `included`(어느 산출물의 어느 절) 또는 `omitted`(사유) 중 하나로 분류돼야 한다.
   ★ **인용 비율이 아니라 처분 완결성이 기준이다** (리뷰 V2-04)

   ```
   page	disposition	output	anchor	reason
   14	included	01_study-guide.md	§2-3
   1	omitted	-	-	표지
   ```

   ★ `page` 는 **PDF 파일의 1-based 페이지 인덱스**다(인쇄 페이지 번호가 아니다).
   ★ **원본 전체 페이지와 대조한다** — `--total-pages` 또는 `--source-pdf` 없이는
   "모든 페이지를 처분했다"를 주장할 수 없다. 게이트가 없으면 거부한다 (리뷰 V21-01)
   ★ `included` 는 **그 산출물의 그 절에 실제로 인용이 있어야** 통과한다 (리뷰 V21-02)

4. **스크립트 검사** — `gate.py --coverage <tsv> <dir> --total-pages N`.
   실제로 검사하는 것만 적는다: **원본 대비** 페이지 처분 완결성 · anchor 실존 ·
   anchor 절 내 인용 실존 · 산출물별 included 집계 · 근거표에 없는 페이지 인용 ·
   필수 목차 · 마지막 h2 규약 · 코드블록 닫힘 · 깨진 상대 링크 · 미완성 표식.
   ⚠️ **"세 문서 용어 일치"는 구현하지 않았으므로 약속에서 뺐다**
5. **다른 모델이 코드·숫자·표는 전수, 페이지는 표본 대조**한다.
   표본은 `max(5쪽, 전체의 10%)` 이고 **수량과 seed 를 기록한다**
6. ★ **반영 후 4번 스크립트를 다시 돌린다.** 이건 리뷰 라운드가 아니라 기계 검증이므로
   항상 수행한다. 여기서 나온 신규 결함은 `post_fix_gate_regressions` 다 — **유출 결함이 아니다**(§8-2)
7. 제출물일 때만 사람이 표본 5~10페이지 최종 확인

> 검토 모델이 무엇인지보다 **원문 페이지까지 역추적 가능한가**가 중요하다.

## 4. 워크로드 B — 코드 프로젝트 (diff 중심)

1. 주 작업자가 **완료 조건 + 필요한 테스트**를 먼저 적는다
2. 주 작업자가 구현하고 **테스트·린트·타입 검사를 실행**한다
3. 다른 모델이 저장소 전체가 아니라
   **`diff` + 변경된 인터페이스의 호출자 + 실패한 테스트**를 리뷰한다
4. 주 작업자가 **차단 지적만** 반영하고 검증을 재실행한다

아키텍처·스키마·마이그레이션일 때만 2번 앞에 설계 리뷰를 삽입한다.
**즉 확장 모드는 기본값이 아니다.**

## 5. 산출물 — 파일 2개


★ **리뷰 로그는 작업별로 격리한다.** 누적 로그는 과거 합의가 현재 요구보다 높은 권위를

## 6. 에이전트 배치 — 고정 역할표 없음

v1의 "Claude = 명세 준수 / Codex = 탐색적" 역할표는 **폐기했다.**
근거였던 AWS 실험은 HTML 게임 2종 대상이었고, 이를 6,000줄 문서 작성과 저장소 아키텍처로
외삽한 것은 비약이다. 48런 중 채점 불일치 1건을 구조적 효과 크기로 읽은 것도 잘못이다.

**대신 현재 능력으로 선택한다.**

| 판단 기준 | 주 작업자 조건 |
|---|---|
| 입력 형식 | 그 입력(이미지·PDF·코드)을 가장 안정적으로 다루는 쪽 |
| 검증 수단 | 테스트·스크립트를 실행할 수 있는 쪽 |
| 산출물 길이 | 긴 산출물을 끊기지 않고 쓸 수 있는 쪽 |

**비평자 조건은 하나뿐 — 주 작업자와 다른 모델 계열.**

> 6~10건에서 역할을 **교차 배치**한 뒤 §8 지표로 갱신한다. 지금 고정하지 않는다.

## 7. 검증된 도구 사실 (2026-09-14)

v1에서 틀렸던 것을 정정한다.

| # | v1 주장 | 정정 |
|---|---|---|
| 1 | Codex는 로컬 이미지를 못 읽는다 | ✅ **틀림.** `-i`/`--image`로 명시 첨부하면 읽는다. 다만 **경로만 적으면 자동 시각 입력이 되지 않는다.** PDF는 페이지 렌더링 후 첨부 또는 PDF 스킬 사용 |
| 2 | Codex는 `AGENTS.md`만 읽는다 | ✅ **불완전.** `AGENTS.override.md` · 계층형 누적 · `project_doc_fallback_filenames`. 32KiB 는 대체 파일명 목록 크기가 아니라 **합산 지침 한도 `project_doc_max_bytes` 의 기본값**이다. `AGENTS.md` 정본 + `CLAUDE.md` 포인터는 **선택지일 뿐 필수가 아니다** |
| 3 | Codex는 스킬을 읽지 않는다 | ✅ **틀림.** `SKILL.md` **지원**(‘완전 지원’은 과한 표현 — 스킬이 많으면 초기 목록에서 일부가 생략될 수 있고 **암시 호출은 보장되지 않는다**). `.agents/skills`(repo·home) · `/etc/codex/skills` 자동 감지, **description 기반 암시 호출**까지 된다. `allow_implicit_invocation: false`로 끌 수 있다 |
| 4 | Codex는 긴 문서에서 끊긴다 | ⚠️ **확인 불가.** 공식 보장 문서 없음. 줄 수로 판단하지 말고 **파일에 직접 쓰기 + 섹션 단위 검증 + 열린 코드블록 검사**로 대응 |
| 5 | SWE-bench 72.7 vs 69.1 | ⚠️ **인용 삭제.** 출처 페이지가 갱신됐고, 표본·신뢰구간 없이 "노이즈"라 부를 근거가 없었다 |

**스킬 전략 (정정)** — 양쪽 다 스킬을 읽으므로 스킬화가 가능하다. 단 **탐색 경로가 다르므로**
(Claude Code `.claude/skills` vs Codex `.agents/skills`) 같은 파일을 자동 공유하지는 않는다.
심볼릭 링크 또는 복제 + 동기화 검사가 필요하다. **항상 적용할 짧은 원칙은 `AGENTS.md`에,
특정 작업에서만 필요한 절차는 스킬에** 둔다.

**샌드박스 권고**

```toml
approval_policy = "on-request"
sandbox_mode    = "workspace-write"

[sandbox_workspace_write]
network_access = false
```

설계·리뷰만 할 때는 `read-only`로 낮춘다. 네트워크는 필요한 단계에서만 켠다.
`danger-full-access`는 이 워크플로우에 필요 없다.

## 8. 시범 운영 — 6건 또는 2주

**이 기간에 추가하지 않는다: Orca 등 ADE · 새 문서 · 새 게이트.**

### 8-1. 비교를 가능하게 하는 메타데이터 (지표가 아니라 조건)

`_templates/metrics.tsv` 한 파일에 기록한다.

```
task_id	date	workload	risk_flags	primary_model	critic_model
valid_findings	false_findings	review_minutes
post_fix_gate_regressions	reaudit_findings	leaked_defects
usage_value	usage_unit	note
```

★ 이게 없으면 6건 뒤에 **"어느 모델을 주 작업자로 둘지"도 "교차 리뷰가 효과가 있는지"도
판정할 수 없다** (리뷰 V2-03). `usage_unit` 은 `tokens` / `requests` 중 하나를 명시한다 —
단위 없는 `total_usage` 는 모델 간 비교가 불가능하다.

### 8-2. 지표

| 지표 | 정의 |
|---|---|
| `valid_findings` | 반영됐거나 반영했어야 했던 지적 |
| `false_findings` | 근거로 반박된 지적 — 리뷰 비용의 분모 |
| `review_minutes` | 비평 + 반영에 든 실제 시간 |
| `post_fix_gate_regressions` | 반영 후 게이트가 잡은 **구조 회귀** |
| `reaudit_findings` | ★ accepted 수정 **재대조**가 추가로 잡은 **내용 오류** |
| `leaked_defects` | 아래 워크로드별 정의 |
| `usage_value` / `usage_unit` | 작업별 사용량 + 단위 |

★★ **`post_fix_gate_regressions` 와 `reaudit_findings` 를 섞지 않는다** (리뷰 V21-03).
v2.1 은 전자를 "워크로드 A 의 유출 결함"으로 정의했는데, 그건 **구조 회귀이지 유출이 아니다.**
그리고 **재대조의 가치는 재대조를 하지 않고는 측정할 수 없다** — 순환 논리였다.

| | `leaked_defects` 정의 |
|---|---|
| **B. 코드** | 반영 후 **7일 내** 테스트·실행에서 드러난 결함 |
| **A. 수업 자료** | ⚠️ **관측 창이 시범 기간을 넘는다**(복습·시험 시점). 6건 동안은 `n/a — 관측창 초과` 로 기록하고, 나중에 발견되면 소급 기입한다. **빈칸으로 두지 않는다** |

### 8-2b. ★ 시범 기간 한정 규칙 — accepted 수정 전수 재대조

시범 6건 동안은 **accepted 로 처리한 수정 전부를 원문에 다시 대조**하고
`reaudit_findings` 에 기록한다. D3(재대조가 필요한가)는 **`reaudit_findings` 와
재대조 시간을 비교해서만** 판정할 수 있다. 6건 측정 후에야 전수 → 표본으로 줄인다.

### 8-3. 판정 규칙 — "0건이면 폐기"는 쓰지 않는다

> **6건은 중단 판정이 아니라 절차 조정용이다.**
> 유효 지적이 0건이고 리뷰 비용이 상한을 넘으면, 전면 폐기가 아니라
> **위험도 2점 이하에서만 교차 리뷰를 비활성화**한다.

0/6 은 "효과 없음"의 증거가 아니다. 희귀하지만 큰 오류를 잡는 리뷰라면 6회 연속 0건도
가능하다. 채택률 100% 역시 **비평자가 정확했을 수도** 있으므로 수렴의 직접 지표가 아니다
— 오탐 지적 수와 함께 봐야 한다.

### 8-4. 갱신 규칙

반복 실패가 **실제로 관측된 지점에만** 게이트·문서를 추가한다.
예상 실패에 선제적으로 파일을 만들지 않는다 (v1 의 가장 큰 오류).

## 11. 이 게이트가 보증하지 않는 것

솔직하게 적는다. 게이트 `exit 0` 은 아래를 의미하지 **않는다**.

| 검사한다 | 검사하지 않는다 |
|---|---|
| 근거의 유형·형식, `path` 파일 실존 | **근거의 사실성** — test 를 재실행하지 않고 인용문을 원문과 대조하지 않는다 |
| 원본 대비 페이지 처분 완결성, anchor 실존, 절 내 인용 실존 | **내용이 정확한가** — 숫자 오독·설명 왜곡은 사람·비평자의 재대조로만 잡힌다 |
| 차단 지적 5건 상한, 라운드 상한, 치명 미합의 중단 | **지적이 옳은가** |
| 구조(코드블록·링크·목차·마지막 h2) | **문서가 읽을 만한가** |

> 이 표를 지우지 마라. v2.1 의 가장 큰 위험은 게이트가 실제보다 많은 것을 보증한다고
> 믿게 만드는 **거짓 안전감**이었다 (리뷰 V2-02·V21-04).
