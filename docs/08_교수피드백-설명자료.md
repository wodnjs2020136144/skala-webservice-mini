## 0. 먼저 말할 것 — 범위와 근거

- **한 줄 정의**: 간호사 교대근무에서 *누가 인계를 맡았고, 누가 받아서 확인했는지*를 남기는 웹서비스. 근무표가 끝나는 지점에서 시작한다.
- **범위**: 국내 종합병원 **병동 한 곳**의 운영 방식 기준. **현직 간호사 한 분** 인터뷰 `[C]`. "간호사 일반"으로 일반화하지 않는다.
- **하지 않은 것**: 근무표 자동 생성 · 병원 전산(EMR) 연동 · 실제 환자정보 · 의학적 판단 · 교육/급여/알람.
- **근거 등급**: `[A]` 원문 확인 · `[B]` 2차 출처 · `[C]` 인터뷰로 확인 · `[D]` 미검증. 등급 없는 문장은 우리 판단.
- **"찾지 못했다"는 "없다"가 아니다** — 국내 병원 전산에 인계 전용 화면이 있는지는 확인하지 못했다 `[D]`. 덱 5장 마지막 행.

## 2. 슬라이드 순서대로 — 각 장에서 정확히 무엇을 구현했나

### 3장 · 무엇을 만들었나
- 정의 한 문장 + 하지 않은 것. **범위를 먼저 닫는다.**

### 4장 · 단어 다섯 개 (듀티 · 차지 · 액팅 · 인계 · 결원)
- 권한의 근거가 되는 구분은 **차지 vs 액팅**: 인계는 차지가 쓰고 다음 근무 차지가 받는다. 액팅은 옆에서 같은 인계를 듣는다 `[C]`.
- 이 사실 하나가 F-06(병동 공통 템플릿)과 읽기 권한 3갈래(10장)를 결정했다.

### 7장 · 불편했던 것, 푼 방법
- 핵심 정정: *"인계 내용이 기록되지 않는다"* 가 아니다. **내용은 전산에 남는다. 없는 건 "받았다"는 기록** `[C]`. 그래서 해결 대상을 *수신 기록*으로 좁혔다.
- 수간호사 쪽 `[D]` 표기 이유: "엑셀을 고치고 메신저로 공지한다"는 전언이라 등급을 낮췄다.

### 8장 · 인터뷰 뒤에 뺀 것 네 가지
- 처음 가정 4개가 인터뷰에서 무너졌고, 각각 **무엇을 바꿨는지**가 적혀 있다. 정합성을 *유지한 기록*이다.
- 특히 *"역할마다 인계 항목이 달라야 한다"* → 아니다 → **템플릿을 역할별이 아니라 병동 공통 한 벌로** 줄였다. 이게 `handover_template_item` 에 `role_type_id` 가 없는 이유.

### 9 · 10장 · 누가 쓰나 / 볼 수 있는 범위
- 사용자 2종: 수간호사(HEAD_NURSE) · 간호사(NURSE). 다른 병동은 **403** — "없는 것처럼(404)"이 아니라 "권한이 없다".
- **읽기 권한 3갈래** (`docs/02` T6 이 단일 출처):
  1. 수간호사 = 자기 병동 전체
  2. 인계의 from/to 당사자
  3. **같은 병동·같은 날·같은 근무조·같은 팀 + 이미 넘어간 인계(`sent_at IS NOT NULL`)**. 작성 중(DRAFT)은 쓴 사람만
- 3번이 없으면 액팅이 인계를 못 읽는다. **권한이 기능을 막은 실수를 두 번 했고 두 번 다 T6 표에서 잡았다.**
- 쓰기는 더 좁다: 쓰기는 담당자만, 확인은 수신자만, **결원(ABSENT)으로 등록된 사람은 받을 수 없다**(403).
- **현장과 다른 점**: 참여자는 같은 병동이면 인계 열람에 권한이 필요 없다고 했다 `[C]`. 우리 ③은 그보다 좁다. 넓히는 건 판정 조건 한 줄이고 데이터 구조는 그대로라 **보완 후보**로 뒀다(T6-b).

### 11장 · 기능 여섯 개
- 열을 짚는다: ID → 하는 일 → 누가 → **화면 번호** → **막힐 때 상태코드**. 빈 칸이 없다.
- F-06 을 F-04 에서 분리한 이유: Actor 가 다르다(수간호사가 정하고 간호사가 쓴다). 한 기능에 묶으면 권한 정의가 안 된다.

### 12~14장 · UI 흐름도
- 화면 11개 전부 한 그림 안. 실선 = 화면 이동, 점선 = 데이터가 넘어가는 길. **점선 4개가 수간호사와 간호사를 잇는다** — 배정 반영 · 필수 항목 적용 · 팀 차지 정보 · 앞 근무 차지 → 뒷 근무 차지.
- 배정은 누르는 즉시 반영. 별도 게시/승인 단계 없음.

### 15장 · 화면 읽는 법 (범례)
- 빨강 = API 호출 · 초록 = 화면 이동 · 파랑 = 막히는 곳. 이후 6장이 이 규칙으로 읽힌다.
- **캡처는 전부 실제로 도는 데모에서 찍었고, 화면에 찍힌 주소가 그대로 OAS 의 주소다.** `tools/deck_check.py` 가 덱의 모든 주소를 OAS `paths` 와 자동 대조한다(불일치 0).

### 16장 · 간호사 첫 화면 (8)
- `GET /me/shifts` 한 번으로 내 근무·역할·우리 팀 환자·받은 인계·보낼 인계. 응답 봉투 `{from, to, shifts}`.
- **버튼 판정을 서버가 내려준다** — 쓰기/확인/읽기 중 무엇을 보여줄지 화면이 계산하지 않는다. 규칙을 한 곳(서버)에 둔다.

### 17장 · 인계 쓰기 (9)
- `POST /handovers` — 작성 시작 시 **병동 템플릿을 복사**해 `handover_item` 을 만든다. 나중에 템플릿이 바뀌어도 이미 쓴 인계는 안 바뀐다.
- 요청에 **받을 사람이 없다.** 서버가 "같은 입원 건의 다음 근무 담당"을 고른다. 없으면 422. 받으면 아무 근무로나 보낼 수 있게 되므로.
- `PATCH /handovers/{id}/items` 임시저장 → `POST …/send` 로 DRAFT → SENT. 넘긴 뒤 수정은 409.
- 필수 항목이 비면 422 + **비어 있는 항목 이름**을 돌려준다.

### 18장 · 인계 받기 (10)
- 화면에 들어오면 `POST …/receipt` 로 **열어본 시각**이 남는다. 조회(`GET /handovers/{id}`)와 **분리**했다 — 수간호사나 액팅이 봐도 "받았다"가 되면 안 되므로.
- `PATCH …/receipt` 에 **수신자가 자기 말로 쓴 요약**(`receiver_summary`) 저장.
- `POST …/receipt/confirmation` 으로 SENT → CONFIRMED. **요약이 없으면 422**, 당사자가 아니면 403, 이미 확인됐으면 409.
- 확인 뒤 **보낸 사람 화면에 요약이 되돌아간다**(read-back). 이것이 첫 번째 불편의 답이다.
- 한계(34장): 요약의 성의는 검사하지 않는다. 남기는 건 "누가 언제 자기 말로 적었는가"까지.

### 19장 · 결원 재배정 (6)
- 네 단계 = API 네 개. **사유를 사람이 쓰는 자리는 결원 등록 하나뿐**, 나머지 세 기록은 서버가 사유를 복사한다. 이력이 한 사건으로 읽히도록.
- 대체자 배정 시 옵션으로 결원자의 역할(차지)을 **덮어쓴다**(`PATCH /shift-assignments/{id}` 재사용). 화면에 "액팅 → 차지"로 표시.
- 인계 이관: 원래 `handover_assignment` 를 지우지 않고 **REPLACED** 로 두고 새 줄을 만든다. 진행 중이던 인계는 **SUPERSEDED** 로 두고 새 담당에게 후속 인계를 **같은 트랜잭션**에서 발행. 후속이 안 만들어지면 전체 실패.
- 완료 확인은 **대체자 없이 못 한다**(422). 완료는 자동 판정이 아니라 사람의 확인 기록.
- **남은 인계는 시스템이 막지 않는다** — 안 넘기는 게 정상인 경우가 있다(그 사이 퇴원). 화면이 "이 사람 이름으로 남은 인계 N건"을 보여주고 사람이 판단. T6-b 에 예외로 기록.

### 20장 · 수간호사 첫 화면 (2)
- `GET /wards/{id}/dashboard` 가 **유일한 화면 전용 API**. 네 군데 데이터를 세는 규칙이 화면으로 흩어지지 않게.
- 타일을 누르면 근거로 내려간다: 근무자 명단·역할별 인원은 `GET /wards/{id}/shift-assignments` **재사용**(새 API 없음), 미확인 인계는 `GET /wards/{id}/handovers?status=SENT`. **숫자와 목록이 같은 조건**을 쓴다.
- 결원 타일만 예외: 접지 않고 항상 보인다. 접히면 "재배정 필요"를 놓친다.
- "인계 미작성 N건"은 **넣지 않았다** — EMR 연동이 없어 "썼어야 했는데 안 쓴 건"을 셀 근거가 없다.

### 21장 · 역할과 인계 담당 정하기 (4)
- 역할은 고르는 즉시 저장(`PATCH /shift-assignments/{id}`). 인계 담당은 `POST …/handover-assignments`.
- **"담당 환자 배정"이 아니라 "인계 담당 지정"** — 환자는 팀이 공동 담당 `[C]`. 여기서 정하는 건 *그 근무에서 이 입원 건의 인계를 맡을 사람*.
- 역할로 강제하지 않는다(차지만 담당 가능, 같은 제약 없음). 차지가 빠지면 누가 올라가는지 확인 못 했고, 확인 못 한 운영 방식을 DB 가 금지하면 안 된다고 봤다.

| 묶음 | 테이블 | 한 줄 |
|---|---|---|
| 조직·사람 | `ward` · `team` · `users` · `role_type` | 병동 → 팀(A/B, 호실 범위로 환자 공동 담당) → 사용자. 역할 3종(차지·서브차지·액팅)은 마스터 |
| 근무·환자·담당 | `shift_assignment` · `inpatient_stay` · **`handover_assignment`** | 누가 언제 어느 근무(D/E/N)에 어떤 역할로. 입원 건(가상, `patient_ref_code` 만). **인계 담당 = 근무 × 입원 건** |
| 인계 | `handover_template_item` · `handover` · `handover_item` · **`handover_receipt`** · `reassignment_log` | 병동 공통 양식 → 인계 1건 → 항목(복사본) → 수신 기록(1:1) → 결원 이력 |

Enum 7: `UserType` · `ShiftCode` · `ShiftStatus`(ACTIVE/ABSENT) · `HandoverAssignmentStatus`(ACTIVE/REPLACED) · `StayStatus`(ACTIVE/CLOSED) · `HandoverStatus`(DRAFT/SENT/CONFIRMED/SUPERSEDED) · `ChangeType`.

### 3-2. 설명해야 할 설계 결정 6개

1. **인계 담당은 사람이 아니라 근무에 붙는다.** `handover_assignment.shift_assignment_id` (FK) + `inpatient_stay_id`. 결원이 나면 근무 줄을 바꾸고 담당을 이관하면 인계가 따라온다. 사람에 붙였으면 "그날 그 근무에서" 라는 조건이 사라진다.
2. **`handover` 의 from/to 도 사람이 아니라 `handover_assignment`** 다. 그래서 "받을 사람"을 서버가 계산할 수 있다(같은 입원 건의 다음 근무 담당).
3. **`handover_receipt` 는 인계당 1건(unique)**, 열어본 시각·요약·확인 시각 세 칸. **첫 번째 불편의 답이 이 테이블이다.** `handover` 안에 컬럼으로 넣지 않은 이유: 수신은 별개의 사건이고, 없을 수 있다.
4. **`handover_item` 은 템플릿의 복사본.** `label`·`is_required` 를 복사 시점에 굳힌다. 양식을 고쳐도 지난 인계가 안 바뀐다.
5. **지우지 않는다(append-only).** 담당 변경은 REPLACED + 새 줄, 인계 대체는 SUPERSEDED + `superseded_by_handover_id`. 확인까지 끝난 인계는 SUPERSEDED 로 못 바꾼다(409). **비용도 적었다**: 남은 줄이 유효한 PK 라 읽을 때·쓸 때·고를 때 "지금 것인가"를 매번 확인해야 한다. **현장 근거** `[C]`: 차지가 카덱스에서 "필요 없겠다" 싶어 임의로 지운 기록이 나중에 중요한 기록이어서 문제가 된 적이 있었다. 참여자도 "넘기고 확인된 뒤엔 본인도 수정·삭제 불가"가 맞다고 했다.
6. **결원 기록은 두 층.** `shift_assignment.status = ABSENT`(근무 자리가 빈 것)와 `reassignment_log`(무엇이 누구에게 넘어갔는지, `ChangeType` 4종: 결원 등록 · 대체자 배정 · 인계 담당 이관 · 대체 완료 확인). 기록 종류 하나가 나머지 칸의 유효 조합을 정한다. 한 컬럼으로 여러 테이블을 가리키는 방식은 FK 제약을 못 걸어서 안 썼다.

### 3-3. 파생값을 컬럼으로 만들지 않은 것
- "미확인 인계 수", "역할별 인원" 은 컬럼으로 저장하지 않고 조회 시 센다. 미확인 건수는 `handover(to_handover_assignment_id, status)` 인덱스로 `status=SENT` 를 세고, 집계식은 바꾸지 않는다고 DBML 주석에 못 박았다.

### 4-3. 요청에서 일부러 받지 않는 값 3개 (31장)
| 값 | 왜 서버가 정하나 |
|---|---|
| 인계를 받을 사람 | 화면이 정하면 아무 근무로나 보낼 수 있다. 같은 입원 건의 다음 근무 담당을 서버가 고르고, 없으면 422 |
| 결원 사유 | 사람이 쓰는 자리는 결원 등록 하나. 나머지 3 기록은 복사. 사유가 갈리면 한 사건으로 못 읽는다 |
| 화면 버튼 판정 | 쓰기/확인/읽기 중 무엇을 보여줄지 서버가 내려준다. 화면마다 판단하면 규칙이 흩어진다 |

**규칙**: 화면이 요청에 넣는 ID 는 반드시 어떤 조회 API 가 돌려준 값이어야 한다. 이 규칙이 없어 생긴 구멍(`from_handover_assignment_id` 를 어떤 조회도 안 돌려줬다)을 검증 단계에서 찾아 `TeamStay` 스키마에 필드를 추가했다.

### 4-4. 상태코드 1:1 (32장) — 명세 안 개수
| 코드 | 뜻 | 이 서비스에서 | 명세 등장 |
|---|---|---|---|
| 401 | 로그인 안 됨 | 모든 요청 | 24 |
| 403 | 있지만 당신은 못 본다 | 다른 병동 · 내 인계 아님 · 액팅이 쓰려 할 때 · 결원자가 받으려 할 때 | 22 |
| 404 | 그런 건 없다 | 없는 번호. 다른 병동을 404 로 숨기지 않았다 | 22 |
| 409 | 지금 상태에선 못 한다 | 재확인 · 대체된 인계 수정 · 퇴원 환자에 새 인계 · 같은 사람 같은 근무 중복 | 12 |
| 422 | 보낸 내용이 모자라다 | 필수 항목 비었음 · 요약 없음 · 대체자 없이 완료 · 다음 담당 없음 | 10 |

409 와 422 를 섞지 않는 이유: 섞으면 화면이 *무엇을 고쳐야 하는지* 모른다. 인계 상태는 DRAFT → SENT → CONFIRMED 로만 간다. 되돌아가지 않는다.

### 4-5. 명세 형식
- 공통 응답 봉투·오류 형식·스키마는 `components` 에 두고 `$ref` 로 재사용한다. 설계 순서는 공통 형식 → 주소였고, 파일 안 순서는 `paths` → `components` 다.
- 로그인·인증은 병원 시스템 몫이라 명세에 없다(가정).
