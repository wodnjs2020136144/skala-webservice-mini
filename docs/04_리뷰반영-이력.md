## R1 / 중 / 필수와 권장의 구분

**판정: accepted.** 타당하다. 특히 위험했던 건 **시간이 없을 때 무엇을 먼저 버릴지 판단할 수 없게 만든다**는 점이다. 3일 프로젝트에서 우선순위 판단 불가는 실질적 위험이다.

**조치**: `[필수] / [권장] / [전략]` 3단 표기 도입. 근거를 다시 확인해 재분류했다.

- `[필수]`로 확정된 것 — 파일명 규격, UI 흐름도 PDF 내 포함, 마감 시각, 교안 목차 8항목, PK/FK·관계 명시, 데이터 타입·제약조건 명시, 적절한 HTTP Method, Path/Query/Body 명확화, **에러 코드 정의**, **공통 스키마 $ref 재사용**, Security Schemes 제외

## R3 / 중 / 절대적 규칙의 완화 (조건부 수용)

**지적 요지**: 아래 4개는 기본 원칙으로는 좋으나 항상 정답은 아니다.
① 파생값은 컬럼으로 만들지 않는다 ② 상태값은 전부 Enum ③ 매핑표에 없는 테이블·컬럼은 삭제 ④ 화면 전용 조회 API가 정답

**판정: accepted — 단, "원칙 약화"가 아니라 "예외의 명시적 기록"으로 수용한다.**

지적 자체는 정확하다. 실제 반례가 존재한다.

- ① **이력 스냅샷** — 주문 시점 가격처럼 *그때의 값*을 보존해야 하는 경우. 현재가로 재계산하면 과거 데이터가 왜곡된다
- ② **사용자가 값을 추가·수정하는 코드성 데이터**(부서, 직급, 카테고리) — Enum이면 값 추가에 배포가 필요해진다
- ③ **감사 로그, 내부 FK, `created_at`/`updated_at`** — 화면에 안 나오는 게 정상이다
- ④ 전용 API가 늘면 **재사용성이 떨어진다**

**다만 수용 방식은 리뷰 제안과 다르게 잡았다.** 규칙을 "~하는 편이 좋다"로 바꾸면 3일짜리 시간제한 프로젝트에서 **매 결정마다 재고하게 되어 속도가 죽는다.** 그래서 **기본값은 원칙 그대로 강하게 두고, 벗어날 때만 사유 한 줄을 남기는** 형태로 반영했다.

**조치**: `02_…템플릿.md`에 **T6-b 설계 예외 기록** 표 신설. 열은 `대상 | 원칙 | 실제 결정 | 사유`.

> 부수 효과가 크다. **T6-b가 그대로 기술서 8장 "설계 상의 고민"이 된다.** 교안이 요구하는 목차 항목 하나가 자동으로 채워진다.
> 무판단으로 남긴 컬럼과 판단해서 남긴 컬럼은 평가자에게 다르게 읽힌다.

**지적 요지**: T9는 UI·API·DB의 **존재 여부**만 확인하고 권한과 상태 전이가 약하다.

**판정: accepted.** 게다가 이건 취향 문제가 아니라 **배점과 직결**된다. 세부 평가 기준에 `에러 코드 정의(400, 401, 404 등)`가 명시돼 있고, `예외/오류 시나리오 포함`은 **가점** 항목으로 적혀 있다. v1은 이 둘을 DBML·OAS 체크리스트에만 흘려 두고 검증 단계에 올리지 않았다.

**조치**

- `02_…템플릿.md` **T9를 (1) 존재 대조 / (2) 정상 흐름 밖 점검** 2단으로 분리

- `00_…가이드.md` 3일차 정합성 블록을 09:00–10:00 → **09:00–10:15**로 확대. R4로 PDF 조립 부담이 줄었으므로 이 15분을 확보할 수 있다
- 상태 전이는 **행=현재 상태 / 열=목표 상태 / 칸=허용·금지+코드** 행렬로 그리도록 안내 — 발표 슬라이드로 바로 쓰인다

## R9 / 치명 / 인과 비약

**판정**: v1은 *"부적응의 상당 부분이 당일 역할을 모른 채 출근하고 비구조화된 인계를 받는 데서 온다"* 고 썼다. **사직 사유 조사는 "업무 과다·부적응"까지만 말하고 내부를 쪼개지 않는다.** 근거 없는 확장이었다.

**조치**: 사실과 가설을 분리. 그리고 **서비스 목표를 "이직률 감소"에서 측정 가능한 4개 지표로 교체**했다 — 역할 확인 소요시간 / 인계 필수항목 누락 건수 / 근무 변경 재공지 횟수 / 오프 중 확인 필요성. 이쪽이 방어하기 쉽고, 발표에서 "그걸 어떻게 측정하냐"는 질문에 답이 있다.

## R14 / 중 / 스코프 축소 — 한 가지만 다르게 수용

**수용**: 기능 5개로 축소, AI는 **SBAR 구조화 초안 + 필수 항목 누락 표시**로만. Out of scope 5줄 확정.

**임상 판단 AI를 빼는 근거 3가지** (리뷰 제안에 근거를 보강함)

1. 운영 가이드가 **"AI 기능이 없는 경우"를 감점 사유가 아니라고 명시**했다
2. 3일 안에 임상 중요도 기준을 세울 수 없고, **"그 우선순위 근거가 뭐냐"는 질문에 답이 없다**
3. **ShiftSBAR가 정확히 "긴급 상태 변화 자동 플래그"를 이미 한다.** 따라 하면서 근거는 더 약해진다

**다르게 수용한 부분**: 리뷰는 "역할별 우선순위"를 **통째로 빼라**고 했으나, 그러면 **직접 관찰한 불편 5번(차지/액팅별로 인계 비중이 다름)이 사라진다.** 방식만 바꿨다.

- ❌ AI가 임상 중요도를 판단해 정렬
- ✅ **수간호사가 역할별 필수 인계 항목 세트를 정의**하고, 그 역할로 배정된 사람에게 해당 체크리스트가 뜬다

**임상 판단이 사라지면서 데이터 모델은 오히려 좋아진다** — `역할 유형 ↔ 인계 항목 정의`가 M:N이 되고 해소 테이블이 자연스럽게 생긴다. 40점짜리 시스템 설계에서 쓸 게 늘었다.

**추가 판단 — 환자 엔티티**: 리뷰의 "실제 환자 개인정보 미사용"은 **데이터의 문제이지 엔티티의 문제가 아니다.** 인계는 환자 단위라 엔티티를 피할 수 없으므로, 피하지 말고 **식별정보를 병상번호 + 환자코드까지만 두고 그 판단을 T6-b에 기록**한다. 개인정보보호법 제23조를 근거로 들 수 있어 "설계 상의 고민" 슬라이드가 강해진다.

## 2라운드에서 배운 것

v1 조사의 실패 패턴은 하나였다 — **"조사 범위를 명시하지 않고 일반화했다."**
국내 20종을 조사해 놓고 "세상에 없다"고 썼고, 앱스토어 설명을 끝까지 안 읽고 "연동 안 됨"이라고 썼다.

재발 방지 규칙 2개를 도메인 조사에 적용한다.

1. **"없다"는 문장에는 반드시 조사 범위를 붙인다.** — "조사한 국내 공개 서비스 20종 중"
2. **공백이라고 주장하기 전에 그 기능을 하는 제품명을 최소 3개 검색해 본다.** — "nurse handoff app", "shift handover SBAR", "nurse assignment AI"

## 남은 리스크

- **국내 EMR(베스트케어 등)의 인계·환자배정 기능 보유 여부는 여전히 미확인.** 공개 자료로는 확인이 어렵다 → **인터뷰 질문 1번**으로 해결한다. 이 답에 따라 A-lite 스코프가 바뀔 수 있다
